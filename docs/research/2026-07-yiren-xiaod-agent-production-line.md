# 亦仁小D：创建一个数字员工的办法（公开材料反推）

| 项目 | 内容 |
| --- | --- |
| 状态 | 已核对，等待作为后续改造依据 |
| 日期 | 2026-07-22 |
| 目的 | 先弄明白亦仁怎样做出一个可交付的员工，再决定 A君、小D 和后续员工怎样改 |

## 先说结论

亦仁的方法不是“先做一个很大的军团系统，再往里塞员工”。

他的顺序更像这样：

```text
先用模板做出一个能完成最小工作的员工
→ 给它定岗位
→ 写清工作步骤
→ 给它独立的大脑
→ 给它需要的手脚
→ 用真实任务反复验收
→ 这个样板稳定后，才复制方法创建下一个员工
```

音视频转录 Agent 的第一关，目标很小：

```text
给它一个公开音频链接
→ 下载音频
→ 转成文字
→ 去掉时间戳
→ 在当前目录生成“转录结果.md”
```

这一步还不是完整的小D，更不是军团。它只是证明“这个员工有大脑、有手脚，真的能做第一件工作”。

我们之前的问题是把“总管、审批、状态、治理、很多岗位”做在了前面，却没有始终把“一个员工能不能自己完成一件明确工作”放在第一位。这样很容易堆出看上去很多、用起来却像固定命令的东西。

## 证据和边界

### 可以确定的部分

1. 亦仁公开的《小D复制部署说明》明确说：小D不是一段提示词，而是一个处理下载、转录、整理和飞书文档交付的 **独立 Hermes Agent Profile**。
2. 公开材料给出的工作步骤是：先找字幕或逐字稿，没有才下载音频并转录；之后清洗、按主题整理、创建飞书文档、检查目录和权限，再交付链接。
3. 你提供的航海课程截图把创建过程拆成六关：
   - 用模板跑通第一个最小 Agent Demo；
   - 定岗位，完成岗位卡；
   - 拆工序，梳理工作流；
   - 写大脑，完成 Hermes Agent Profile；
   - 接工具，用 Codex + 飞书 CLI 装上手脚；
   - 跑闭环，完成测试、优化和交付复盘。
4. 课程的第一关明确要求：独立 Hermes Profile、对应飞书 Bot、私聊接通、最小音频转录任务和能力边界说明。群聊接通是进阶内容，第一关不把它作为必过条件。
5. 课程中的 Codex 会生成飞书授权链接并继续配置；但创建飞书应用时，使用者仍要在飞书页面完成授权、填写应用名称并点击创建。它是“Codex 带着做”，不是无须人工确认的全自动开户。

### 不能装作已经知道的部分

- 我们看不到亦仁的私有配置、模型选择、完整提示词、全部工具和真实调度代码。
- 公开材料证明的是他的产品方法和一套小D样板，不足以证明他内部使用了 Paperclip、某一种多 Agent 框架，或每个员工都完全一样搭建。
- “让 Codex 创建飞书 Bot”是你给出的课程指令；公开资料没有证明这个步骤在所有飞书租户都能全自动完成。真实创建仍可能需要人在飞书后台确认权限或发布。

因此，下文是有证据的“创建方法模板”，不是假装拿到了亦仁的源代码。

## 两层顺序：为什么“先建 Profile 和 Bot”与“第一关先做本地 Demo”不冲突

这两件事说的是两层不同的事：

```text
接线层：先有独立员工工位和飞书门口
工作层：先证明这个员工能完成最小工作
```

| 层次 | 做什么 | 什么时候算通过 |
| --- | --- | --- |
| 接线层 | 创建独立 Hermes Profile、飞书 Bot，先测私聊 | 能收到消息，也能回一条普通消息 |
| 工作层第一关 | 让员工本机完成一个最小产物 | `转录结果.md` 真正存在、内容可读 |
| 完整岗位 | 加入岗位标准、飞书文档交付、权限检查和失败处理 | 用户能收到并打开最终产物 |

所以“接通 Bot”不是完成，“能说话”也不是完成。真正完成的标志始终是：用户拿到了可用结果。

## 亦仁小D的完整创建流程（反推版）

### 第 0 步：先搭员工的空工位

给 Codex 的起始要求大意是：

```text
创建一个 Hermes Agent：音视频转录 Agent。
给它独立 profile。
创建对应飞书 Bot。
先完成私聊接通测试；群聊按需要再接。
角色能力、规则和工具后续再补。
```

这一步的产物应该是：

- 一个不和普通助手混用的 Hermes Profile；
- 一个只属于这个员工的飞书入口；
- 私聊能收能回；
- 需要团队共用时，再增加“群聊只在被 @ 时回应”；
- 一张接通记录：至少记下私聊测试；有群聊时再记群聊测试。

它的目的不是让员工立刻什么都会，而是避免后续员工共用大脑、记忆、飞书入口和权限。

### 第 1 关：跑通最小可用样板

先只做一个小任务，不要求飞书文档、复杂审批或多人协作：

```text
下载一个已授权公开链接的音频
→ 用语音转文字工具转录
→ 去掉时间戳
→ 把结果保存成固定文件
```

课程里的要求“开始前先告诉我准备怎么做，确认没问题再继续”，是在验证两件事：

1. 员工能先理解任务并说出计划；
2. 员工不会未经确认就开始消耗资源或操作外部内容。

第一关只需要证明它能产出文件。不要一开始就要求“像人一样会所有视频平台、会自动写飞书文档、会管理军团”。

### 第 2 关：定岗位，写岗位卡

把“它是音视频助手”变成可执行的岗位说明：

- **它接什么：** 音频、视频、播客、会议录制、飞书妙记、网页链接、本地文件；
- **它交什么：** 原始转录、整理稿、飞书文档链接；
- **它不做什么：** 绕过登录/付费/地区限制，擅自外发或公开发布；
- **什么算完成：** 文件存在、内容正常、文档能打开、接收人有权限；
- **遇到不行怎么办：** 说明素材为什么拿不到、缺什么授权或材料，不能编造完成。

岗位卡的价值是：以后新增一个员工时，复制的是“写清输入、输出、边界和完成标准”的方法，不是复制小D的业务代码。

### 第 3 关：拆工序，写工作流

公开材料里的小D工作流是：

```text
收到链接/文件
→ 判断来源和是否可访问
→ 优先找字幕或已有逐字稿
→ 没有才下载音频
→ 检查格式、大小、时长和可读性
→ 转录
→ 清洗错字和噪音
→ 用主题整理成可读文稿
→ 自检内容
→ 创建飞书文档
→ 检查目录和访问权限
→ 交付链接
```

这里最重要的不是步骤多，而是每一步都能回答：

- 这一步做成了吗？
- 做不成时，下一步谁来补什么？
- 已经做成的步骤，重试时会不会重复做、重复交付？

### 第 4 关：写大脑，完成独立 Hermes Profile

这一步才是给员工写“怎么思考、怎么说话、怎么做判断”的说明。

小D的大脑不需要假装无所不能。它应该固定理解：

- 自己只负责音视频整理；
- 能拿字幕就别重复下载和转录；
- 没权限就说明问题，不钻空子；
- 整理稿要忠实保留原意，不能胡编或强行压成摘要；
- 长文放文档，不在聊天里刷屏；
- 没有检查文档和权限，不许说“已完成”。

这就是“智能体”和“固定脚本”的分界：

```text
边界、权限、完成标准固定
边界以内的理解、选择和执行顺序由 AI 决定
```

### 第 5 关：接工具，装上手脚

公开材料推荐的手脚包括：

- 下载和处理媒体；
- 音频转文字；
- 创建、写入和检查飞书文档；
- 管理文档访问权限；
- 需要时读取飞书妙记或会议材料。

重点不是必须使用某一个命令，而是每个工具只拿完成岗位所需的最小权限。例如小D可以创建交付文档，却不能擅自把内容公开发布。

### 第 6 关：跑闭环、优化、复盘

一个员工只有同时通过下面这些，才算“可以上岗”：

1. 私聊入口真能用；需要团队共用时，群聊入口也真能用；
2. 最小任务能真做出产物；
3. 最终交付物能打开、内容合格；
4. 用户有访问权限；
5. 给错链接、没权限、转录失败时会诚实说明，不会装完成；
6. 改进一次后再跑一遍，确认没有把旧问题带回来。

## 可复用的“创建一个员工”模板

以后无论是小D、资料研究员、技术专家还是别的岗位，都先填完下面这张表，再创建。

| 项目 | 必须写清的话 |
| --- | --- |
| 员工名字 | 用户在飞书里叫它什么；内部唯一名字是什么 |
| 一句话职责 | 它替负责人稳定完成哪一件重复工作 |
| 最小样板 | 第一次只做什么，交出什么文件/文档 |
| 输入 | 用户必须给什么；缺什么时问什么 |
| 最终交付 | 用户最终能拿到、打开、使用什么 |
| 不做什么 | 登录绕过、外发、发布、付费、删除、敏感读取等边界 |
| 工作步骤 | 从收到任务到交付的 5–12 个可检查步骤 |
| 大脑说明 | 怎样理解任务、何时追问、何时拒绝、怎样检查质量 |
| 手脚 | 允许用哪些工具；每个工具能读什么、写什么 |
| 独立工位 | 独立 Hermes Profile、独立工作目录、独立记忆 |
| 飞书入口 | 独立 Bot 还是先由总管转交；私聊规则；群聊是否必须 @ |
| 私聊测试 | 一条无敏感测试消息：收到、理解、回复是否通过 |
| 群聊测试 | 需要团队共用时才做：一条 @ 测试消息，确认只在被 @ 时回复 |
| 业务测试 | 一条真实但低风险的样板任务：产物是否存在、是否可用 |
| 交付测试 | 文档/文件能否打开；接收人是否有权限 |
| 上线条件 | 私聊、业务和交付测试全过；需要群聊的岗位再加群聊测试，才可显示“可直接交代工作” |
| 失败处理 | 会留下什么记录；能安全重试几次；何时交给技术专家 |

## 当前项目：现有小D与课程接线样板，逐项对照

下面只记录这次能查到的证据；“文件写了”不等于“现在飞书里一定还能用”。

先分清两个对象：

```text
xiaod：已有的音视频业务员工，已经有转录、整理和交付能力。
av-transcriber：按课程第一步新建的接线样板，只有独立工位和飞书收发，故意没有业务工具。
```

这不是意外重复创建。`av-transcriber` 的职责就是证明“新员工如何从零接通”；在负责人补充岗位能力前，它不能接转录工作，也不能和 `xiaod` 合并或互相借凭据。

| 亦仁的关卡 | 当前项目已有证据 | 真实差距或风险 |
| --- | --- | --- |
| 独立员工工位 | 当前机器上确有 `xiaod` 原生 Hermes Profile；另有 `av-transcriber` 独立 Hermes Profile 和独立飞书应用。后者正是课程“先建工位和入口”的样板 | 两者的分工在 `agents/README.md`、`agents/av-transcriber/README.md` 和接线交接单里已经写清；后续只需避免把 `av-transcriber` 误路由成正式小D |
| 私聊/群聊接通 | M1 验收记录证明小D传统机器人私聊消息、模型回复、短媒体和长媒体任务曾真实跑通；`av-transcriber` 接线交接单记录了私聊与群内 @ 的真实收发 | 课程第一关只要求私聊；`av-transcriber` 已额外完成群聊接线，这是更高一层的接线证明，仍不代表它有转录能力 |
| 最小样板 | 现有小D服务能创建任务、获取/转录/整理并生成本地产物；`av-transcriber` 已完成“接线样板”，但工具白名单为空 | 课程的下一步应由 `av-transcriber` 跑一条极短的“生成转录结果.md”样板；在岗位能力、工具和任务规则写清前，不能直接给它复用小D能力 |
| 岗位卡 | `agents/xiaod/manifest.json` 已写明职责、禁止事项、工具范围、质量门槛和预算边界 | 当前项目交付定义是“原始转录 + 结构化整理”，与亦仁公开材料的“分享式提纯原文”不完全相同；这是产品选择，必须明确选哪一个，不能混着说 |
| 工作流 | 现有小D服务有获取、转录、整理、交付、失败恢复等阶段与任务记录；接线教程也明确把“接线”和“业务能力”拆开 | 很多业务步骤仍在服务里固定执行。这没有错，但要想达到课程中“先讲计划、确认后再干”的体验，需要把小D的自然语言理解和计划确认单独补齐 |
| 大脑（Profile） | `xiaod` 有系统说明、任务说明和本机 Hermes Profile；`av-transcriber` 有只允许接线回报的独立 Profile | 小D的飞书媒体附件目前会被直接送进固定流程，绕过普通 AI 对话。这对防重复执行有好处，但它还没有证明能先自然理解各种任务说法、解释计划、确认后再执行 |
| 工具与飞书文档交付 | 小D已有本地媒体处理链和飞书文档创建/权限交付的真实历史验收；`av-transcriber` 刻意保持空工具白名单 | 现有实现主要是自建业务服务直接调用工具，不是 Hermes 通过已整理好的 Skill 自主选工具。结果可以一样，但“员工如何自主判断”的体验还没有被证明 |
| 质量与复盘 | 有自动化测试、失败恢复、短媒体/长媒体历史验收；`av-transcriber` 的接线、业务、上线状态也明确分开写 | `xiaod` 自己的文档仍有旧状态没有同步：Manifest 写 `active`，Profile 映射写 `draft`，`agents/xiaod/README.md` 仍写“未上线”。这是小D旧文档需要收敛，不是 `av-transcriber` 的定位不清 |

## 对当前项目最重要的三条纠偏

1. **保留两条线，不要误合并。**
   `xiaod` 是已有业务员工；`av-transcriber` 是按课程创建的新员工接线样板。后者在负责人定义岗位前必须保持 `draft` 和空工具白名单，不能被总管派去做转录。

2. **把“最小样板”固定下来。**
   下一步不应直接重做现有小D，而应让 `av-transcriber` 按课程跑一条公开短素材：计划说明 → 确认 → 生成本地 `转录结果.md`。这条不过，不给它接小D现有业务能力。

3. **样板通过后，再决定怎样升级。**
   只有 `av-transcriber` 通过岗位卡、工作流、工具边界和真实素材验收，才决定它是独立新员工，还是吸收为下一代小D。不能现在就给小D硬塞新大脑，也不能让新 Agent 偷用旧小D的凭据和入口。

## 后续创建其他员工时的正确顺序

不要先说“创建一个资料员/技术专家”，然后马上给它一堆权限、接 Paperclip、接总管。

应该按下面顺序：

```text
选一个真实重复工作
→ 写最小样板任务
→ 建独立 Profile 和飞书入口
→ 私聊先接通；需要团队协作时再接群聊
→ 跑最小样板并拿到真实产物
→ 写岗位卡、工作流、大脑和工具边界
→ 跑完整交付、失败和权限测试
→ 才允许总管把真实工作交给它
```

这样扩出来的才是员工；跳过中间几步、只生成名字和审批卡的，只是空壳。

## 本轮结论

当前项目已经具备不少小D的“手脚”和部分接线，也已经按课程第一步创建了 `av-transcriber` 这个独立接线样板，不是从零开始。此前的问题不是“多建了一个小D”，而是我们没有把这两条线的目的讲清楚。

因此，下一步不应该立刻继续加 A君规则或再新建岗位。应该先让 `av-transcriber` 按课程完成第一条最小转录样板；通过后，再按岗位卡、工作流、工具边界和完整交付逐层升级。`xiaod` 保持现有稳定业务，不作为这次课程样板的试验田。
