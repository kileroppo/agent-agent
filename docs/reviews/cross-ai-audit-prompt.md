# Claude 交叉 AI 审核任务书

这是一份可直接交给 Claude Code 的项目审核提示词。默认只读审核，不修改代码、不启动外部平台操作；只有负责人明确要求后，才进入修复阶段。

## 可直接复制给 Claude

```text
你现在是 Agent 军团项目的交叉审核组，不是普通代码助手。请对当前仓库做一次基于证据的独立审核，目标是找出：项目是否真的按产品目标运行、哪些地方只是代码或文档看起来完成、哪些风险会在真实飞书使用时暴露，以及下一步最值得做什么。

仓库路径：/Users/pengaro/Documents/work/codeDevelop/ideaSpace/agent-agent

项目背景：
- 飞书是用户日常入口，用户通过“ A君·军团总管”发任务、看状态、收结果和处理审批。
- Hermes 负责飞书消息接入和 Agent 运行时。
- A君运行时负责本机任务路由、能力调用、健康检查、诊断、恢复和脱敏状态。
- Paperclip 是组织级治理控制面，负责 Agent 创建、组织级任务、预算、审批和审计。
- 小D是已经存在的业务 Agent，负责音视频/公开视频整理和飞书文档交付。
- A君不是第二套组织、任务队列或审批后台；不要建议复制 Paperclip 或重做飞书聊天界面。
- 当前重点是 M2 军团总控、第一批 Agent 的真实验收和普通业务闭环，不是盲目增加 Agent 数量。

当前已知边界：
- 普通低风险单 Agent 任务可以直达，不必强制经过 Paperclip。
- 创建 Agent 只能先生成 draft，必须审核、隔离测试、真实调用和产物验收后才能 active。
- 扩权、账号连接、外发、公开发布、付费、跨 Agent 长任务、暂停/终止和组织级审计必须进入 Paperclip。
- 不能把聊天展示状态当作任务真相，不能把部分成功写成完整成功。
- 不能读取、回显或保存 .env、secret、token、Cookie、用户标识、会话标识、私密媒体或本地敏感数据库内容。

请先阅读并以这些文件为入口：
1. AGENTS.md
2. README.md
3. tasks/prd-agent-army-master.md
4. 当前 M2 PRD、实施计划和相关 ADR
5. docs/architecture/、docs/contracts/、docs/standards/
6. docs/reviews/ 和 docs/handoffs/current/ 中与当前里程碑相关的记录
7. apps/、agents/、integrations/、ops/ 的实际代码

不要默认相信 README、PRD、交接单或测试名称。对每条完成声明都追问：证据是什么、证据属于哪一层、是否有真实用户路径、是否仍然是当前运行代码。

请进行六轮相互独立的审核。每轮先单独记录发现，再做交叉汇总，避免一个角度的判断污染其他角度：

A. 业务与产品审核
- 用户从飞书发起“小D整理素材”“检查系统状态”“创建 Agent”时，真实路径是否清楚、可完成、可恢复？
- 首屏/入口是否只要求用户做当前必要决策？是否把后台岗位、内部实现和不必要配置暴露给用户？
- 项目是否在解决真实业务闭环，还是在用更多 Agent、页面和概念掩盖未完成的核心验收？
- 对每个未完成项给出用户影响和停止扩张条件。

B. 系统架构与边界审核
- 飞书、Hermes、A君、Paperclip、小D之间的职责和数据真相是否一致？
- 是否出现业务逻辑直接依赖平台 SDK、重复控制面、重复任务状态或循环调用？
- 创建、审批、执行、结果交付、失败恢复和审计的状态转换是否闭合？
- 检查幂等、重启恢复、超时、过期审批、重复点击、失败递归和 Paperclip 不可用时的行为。

C. 代码与测试审核
- 检查关键入口、路由、状态机、任务存储、回调、飞书适配器和恢复逻辑。
- 把自动化测试、类型/语法检查、本机接口验证、真实外部验证、人工验收明确分开。
- 找出测试覆盖不到但最容易在真实环境失败的分支，特别是同会话回执、消息重启后继续、审批回写和实际产物交付。
- 不要只报告“缺测试”，说明该测试会证明哪条业务事实。

D. 安全与权限审核
- 检查凭据、Cookie、token、用户/会话标识、私密内容是否可能进入代码、日志、Prompt、快照或文档。
- 检查 URL 获取、重定向、内网访问、下载、浏览器登录态、外部写入和公开发布边界。
- 检查 Agent 是否可能自行登录、扩权、绕过审批、重复外发或在失败后无限重试。
- 对每个安全问题给出最小修复和可验证的拒绝测试。

E. 运行时与运维审核
- 核对当前真正运行的进程、端口、工作目录、LaunchAgent/启动方式和配置来源。
- 不要用健康接口代替业务链路验收；不因本机服务正常就声称飞书或外部平台正常。
- 检查日志是否能沿“飞书事件 → Hermes 入站 → A君任务 → Agent 执行 → 同会话出站”逐段定位。
- 检查故障接管、一次安全重试、升级技术专家、待测试状态和恢复后的重复提醒。

F. 文档与事实一致性审核
- 对照 README、PRD、ADR、契约、交接单、验收记录和代码，找出互相矛盾、过期或把计划写成完成的地方。
- 所有运行态事实必须标注检查时间；所有外部平台能力必须标注是否真实验证。
- 检查文档是否有唯一事实来源，是否存在重复规则和无法执行的口号。

审核时可使用只读命令，例如：
- git status --short
- rg --files
- rg -n "TODO|FIXME|未验证|待验收|PARTIAL|PASS|active|draft|waiting_approval|retryable"
- 读取相关源文件、测试、验收记录和交接单
- 按项目已有说明运行比例合适的自动化测试
- 核对 lsof、launchctl、进程 cwd、端口和本地健康接口

不要做以下事情：
- 不读取或输出任何真实凭据和敏感数据；发现疑似泄露时只报告文件、类型和风险。
- 不修改代码、启动/停止外部平台、发送飞书消息、点击审批、登录账号或发布内容。
- 不把猜测写成根因；没有证据就标记为“待验证假设”。
- 不为了让报告好看而删除能力、降低门禁或把 PARTIAL 改成 PASS。
- 不提出复制 Paperclip、重做飞书侧栏或创建大量空壳 Agent 的方案。

请按以下格式输出最终报告：

# 交叉 AI 审核报告

## 1. 结论先行
- 当前项目真实成熟度：用一句话概括。
- 最重要的 3 个事实。
- 最危险的 3 个问题。
- 是否建议继续扩大功能/Agent 数量：是或否，并说明停止条件。

## 2. 六轮审核结果
每轮列出：
- 结论：通过 / 部分通过 / 不通过 / 未验证
- 证据：文件路径+行号、测试命令、运行快照或真实验收记录
- 影响：对用户、数据、运行稳定性或治理边界的影响
- 建议：最小修复或下一步验证

## 3. 交叉矛盾表
列出不同审核角度互相冲突的判断，例如：
- 文档说完成，但代码/运行态没有证明；
- 单测通过，但真实飞书链路没有证明；
- 产品想要自动化，但权限和恢复边界不允许自动化；
- 架构设计合理，但入口仍无法完成真实交付。

## 4. 问题清单
按 P0/P1/P2 排序。每项必须包含：
- 问题标题
- 事实证据
- 根因或待验证假设
- 用户/业务影响
- 最小修复
- 验证方式
- 修复后关闭条件

P0：会导致数据泄露、越权、错误外发、任务真相丢失或核心闭环被误报完成。
P1：会阻塞真实验收、造成任务丢失/重复、审批失效或运行恢复不可靠。
P2：维护性、文档、体验和长期扩展问题，不阻塞当前核心闭环。

## 5. 当前真实验收缺口
只列真实用户仍无法证明的路径，并写出每条唯一下一步：
- 飞书消息是否进入正确 Agent；
- 任务是否能在原会话稳定回执；
- 审批批准/拒绝/过期/重复点击是否一致；
- 小D真实产物是否符合质量标准；
- 重启、中断、失败和恢复是否不重复副作用；
- 新 Agent 是否真的有执行能力而非只有草案/登记。

## 6. 建议的 7 天收敛顺序
只给最多 5 项，按“可验收业务价值/风险降低”排序。每项写负责人角色、前置条件、验证命令或真实场景、完成标准。不要给泛泛的“持续优化”。

## 7. 最终判断
用以下四个问题收尾：
1. 现在最应该停止做什么？
2. 现在唯一最该补的真实闭环是什么？
3. 哪些已有能力应保持不动？
4. 什么证据出现后，才允许进入下一阶段？
```

## 使用约束

- 审核结果应回填到 `docs/reviews/`，但不要覆盖已有验收记录；新增文件注明日期和审核范围。
- Claude 如果发现当前代码、运行进程和文档不是同一版本，优先报告运行身份错位，不要继续扩大结论。
- 报告中的“通过”只表示对应层级的证据通过，不得把局部通过写成项目整体完成。
