# ADR-0001：控制面、运行时与交互通道分离

| 字段 | 内容 |
| --- | --- |
| 状态 | 已接受；Paperclip 进入 M1 的时点由 ADR-0002 修订 |
| 日期 | 2026-07-18 |
| 决策人 | A 君 |

## 背景

Agent军团需要同时解决用户交互、Agent 执行、组织任务治理和业务交付。把这些职责全部塞进小D应用或某一个框架，会让后续扩编、权限治理和平台替换成本过高。

## 决策

- 飞书作为主要交互通道；
- Paperclip 作为组织与任务治理控制面；
- Hermes 作为 Agent 运行时；
- 业务 Agent 只实现领域流程；
- 所有平台通过适配层连接标准任务、产物和审批契约；
- Codex 或其他工程模型作为建设工作台，不作为线上任务控制面。

## 考虑过的方案

### 单一应用承载全部能力

前期简单，但业务、组织、通道和运行时强耦合，第二个 Agent 开始就会复制问题。

### OpenClaw 直接作为统一底座

具备可评估的网关和多 Agent 能力，但没有证据证明它是参考系统既定底座，也尚未用同一真实任务验证。当前保留为候选，不直接采纳。

### 分离控制面、运行时和通道

边界清楚，平台可替换，适合从一个真实 Agent 渐进扩展。代价是需要维护适配器和最终一致性。

## 后果

- M1 先验证飞书、Hermes 与业务执行器，Paperclip 按 ADR-0002 从 M2 接入；
- 必须定义统一任务 ID、状态映射和补偿机制；
- 不允许业务代码直接依赖 Paperclip 或飞书 SDK；
- 未来替换平台不应改变小D领域逻辑；
- 如验证证明某平台无法承担既定职责，需要新 ADR 调整，而不是静默改架构。
