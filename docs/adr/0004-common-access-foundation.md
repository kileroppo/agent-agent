# ADR-0004：通用账号连接、内容获取与运维观察边界

| 字段 | 内容 |

## 背景

小D之外的业务 Agent 同样需要读取登录后的网站、视频、笔记、帖子和其他软件数据。若每个 Agent 直接绑定 MediaCrawlerPro、`yt-dlp`、CookieBridge 或浏览器工具，将产生重复登录、凭据扩散、工具替换困难和故障重复排查的问题。

MediaCrawlerPro 对固定中文平台可提供深度内容与评论；通用工具对更广来源提供正文、媒体或字幕能力。两者能力范围不同，不能让业务 Agent 自行决定或假设同一深度。

## 决策

- M2 建立账号管家、内容获取中心和 Agent 运维官三项跨 Agent 公共能力；
- 登录状态可以由受控浏览器、OAuth、CookieBridge 或其他本机导入适配器接入，但原始凭据只留在受控存储；
- 所有 Agent 只通过平台无关契约请求连接和内容，不直接调用或依赖底层工具；
- 内容获取中心固定执行“MediaCrawlerPro 深度通道优先、通用通道兜底”的路由策略；
- 通用通道按已登记能力交付内容；除非明确请求的能力无任何允许通道可提供，否则不将其描述为内容失败；
- 运维官只使用脱敏健康事件进行通知、诊断、低风险重试和 A君自管组件恢复。

## 考虑过的方案

### 每个 Agent 自己调用工具

初期接入快，但凭据和平台逻辑会复制到每个 Agent，工具替换和运维成本持续增加，不采用。

### 通用通道优先，深度通道补充

会造成重复获取，并使固定平台无法优先获得评论等深度内容，不采用。

### 深度通道优先，通用通道兜底

固定平台优先发挥 MediaCrawlerPro 的深度能力，同时保留广泛来源能力，采用。

## 后果

- 适配器必须声明平台覆盖、能力范围、访问模式、优先级和健康状态；
- 新平台主要通过新增或调整适配器完成，不修改所有业务 Agent；
- 账号管家、内容获取中心和运维官仍待实现与真实验证；
- 不得把已登录浏览器、工具健康或通用内容包当作具体业务任务已经成功的证据。
