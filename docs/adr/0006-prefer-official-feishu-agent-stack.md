# ADR-0006：优先采用飞书官方 Agent 能力，不重复建设消息与工具底座

| 字段 | 内容 |
| --- | --- |
| 状态 | 已接受，分步替换 |
| 日期 | 2026-07-22 |
| 决策人 | A 君 |
| 关联 PRD | `tasks/prd-agent-army-master.md`、`tasks/prd-m2-first-batch-agent-governance.md` |

## 背景

现在的 A君 已经能通过 Hermes 在飞书收消息、回消息和处理审批卡。但这些接线依赖一份对 Hermes 安装目录的补丁。它能用，却会随着 Hermes 升级而需要重新检查，也让“多个真正员工在飞书里协作”变成重复配置。

飞书官方已经提供了专门给 Agent 使用的现成能力：

- **飞书 Channel SDK**：收消息、去重、回消息、卡片按钮、流式回复、群聊和 @ 提及；
- **一键创建飞书应用**：按员工岗位创建或更新机器人应用，并预设权限、事件和卡片按钮；
- **飞书 CLI**：让已经获准的员工操作文档、日历、任务等飞书内容；
- **Agent@Agent 协作方式**：总管在群里 @ 有真实能力的员工，员工间接力，负责人可随时看见和纠正过程。

这些正好覆盖我们此前正在手工维护的“聊天接线”和“飞书工具调用”，不应再复制一套。

## 决策

1. **保留当前能工作的 A君入口，不做一次性推倒。** 当前 Hermes → A君 的真实私聊和审批卡继续运行；只有新的官方接线通过本机检查和一次真实飞书回归后，才逐步替换补丁。
2. **新增一层统一的飞书收发入口，优先接飞书 Channel SDK。** 它只负责收消息、去重、群聊 @ 判断、卡片按钮和把回复送回原聊天；A君 仍负责理解、分工和状态，Paperclip 仍负责组织级审批、预算和审计。
3. **员工应用先做“最小需要”，不默认拿一大堆权限。** 创建新机器人时使用官方一键创建能力的最小模式，只按该员工真实工作申请消息、卡片或群内 @ 等必要权限；创建操作只准备草案，最终扫码确认仍由应用所有者完成。
4. **飞书里的真实协作先从一个小队开始。** 日常仍以 A君 私聊为主；需要多人协作时建立“军团协作群”，由 A君 @ 已通过真实验收的业务员工，过程可见。只有小D、公开资料报告员这类真正能交付工作的员工，才考虑独立机器人入口；运维官、审核官、架构师、技术专家继续是后台岗位，不制造空壳聊天机器人。
5. **飞书 CLI 只做获准动作的执行手。** 它不保存任务真相、不自行审批、不直接暴露账号信息。员工的允许动作、审批结果和审计仍由 A君/Paperclip 管住；先从只读文档、任务等低风险动作开始。
6. **不采用 Vercel Chat SDK。** 本项目没有在用它；再引入一套聊天状态和界面会和已有任务/会话记录重叠。直接采用更小的 Channel SDK 更合适。

## 考虑过的方案

### 继续给 Hermes 打越来越多补丁

短期快，但消息、卡片、多人协作和升级兼容都要自己长期维护，不采用。

### 每位员工都立刻做一个飞书机器人

看起来热闹，但大多数岗位当前没有可独立交付的业务能力，会制造空壳员工，不采用。

### 引入一整套新的聊天前端

会把飞书已有的聊天、卡片和会话能力又做一遍，也会和现有任务记录产生两套状态，不采用。

### 使用官方收发、建应用和工具能力，保留现有军团分工

飞书处理它擅长的聊天和飞书内容；A君/Paperclip 保留军团的判断、治理和任务真相。先小范围替换，再做真实回归，采用。

## 落地顺序与验收

1. 做出“员工需要什么飞书能力”的本地草案和检查，不创建外部应用；
2. 用 Channel SDK 做与当前 A君入口相同的受控收发接线，并用自动检查覆盖消息、卡片和原会话回复；
3. 先为一位已能真实交付的员工创建最小飞书应用，完成私聊或群内 @ 的真实回归；
4. 建立一个小型协作群，验证 A君 → 员工 → A君 的可见接力；
5. 再接入飞书 CLI 的只读动作；写入、外发、付费、扩权等动作继续先走审批。

每一步的外部扫码、应用创建、群聊配置和真人点击，均登记到统一验收账本；外部条件未具备时标为待测试，其他步骤继续。

## 后果

- 当前 Hermes 补丁从“长期方案”降为“过渡方案”，不得继续往其中堆新业务逻辑；
- 新员工是否有独立飞书入口，取决于它是否已有真实能力和验收，而不是岗位名称；
- 要维护一份不含凭据的员工飞书能力草案，便于最小权限创建和复核；
- 真实应用创建、用户授权和飞书 CLI 的个人数据访问，不能由模型在聊天中自行完成。
