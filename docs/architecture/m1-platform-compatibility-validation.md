## 1. 验证结论

现有三层边界仍然成立：飞书负责交互，运行时负责任务执行，控制面负责组织治理。但当前版本 Hermes 的能力比原设计假定的更完整：它已经包含飞书 Gateway、多 Profile 路由、持久任务板、调度、heartbeat、重试和运行历史。

已确认采用：

- **M1：** 飞书 + Hermes Profile/Gateway/Kanban + 小D业务执行器完成实际闭环；
- **M2：** 再接 Paperclip，负责组织树、岗位归属、预算硬限制、审批治理和跨 Agent 审计；
- **Lark CLI：** 作为飞书业务对象工具层，用于文档、云盘、权限、审批等动作，不再另做消息总入口；
- **任务真相：** M1 执行任务与运行历史由 Hermes Kanban/本地业务状态承载，产物与 checkpoint 由业务存储承载；飞书只做展示；Paperclip 接入后只承载组织治理投影，不复制细粒度执行状态。

这个方案避免 M1 同时维护 Paperclip 与 Hermes 两套任务队列。正式决策记录见 [ADR-0002](../adr/0002-phase-paperclip-after-m1-runtime-closure.md)。

## 4. 为什么不建议 M1 双任务控制面

如果 Paperclip 和 Hermes Kanban 同时创建并推进同一任务，会出现：

- 两边状态哪个算真相不清楚；
- 重试、取消和恢复可能重复执行；
- heartbeat 与失败历史重复记录但无法一一对应；
- 小D尚未跑通时，先花时间维护同步补偿。

M1 的主要问题是验证一个真实 Agent 闭环。先让 Hermes 承载运行任务，让 Paperclip 在多 Agent、预算和组织审批真正出现时接管治理，能保留长期方向并降低第一阶段耦合。

## 6. 仍需真实验证

只读能力存在不等于闭环可用。进入编码前仍需一次受控验证：

1. 更新或隔离运行 Lark CLI 当前稳定版，确认与租户兼容；
2. 已创建并发布最小权限飞书测试应用；
3. 已建立独立 `xiaod` Hermes Profile，未复用个人默认 Profile；
4. 验证飞书消息接收、用户准入、卡片回调和回复；
5. 验证文档创建、内容写入、权限授予和接收人可读；
6. 验证 Hermes Kanban 的幂等创建、调度、失败、重试、取消和重启恢复；
7. 用一个短素材完成小D端到端冒烟，不做公开发布或高成本任务。

上述步骤会创建本地配置或外部飞书资源，需要单独执行授权。

## 7. 安全与部署约束

- 飞书 App Secret、用户 token 和模型密钥只进入隔离环境配置；
- Hermes Profile 是配置隔离，不等同于文件系统沙箱；
- 飞书用户准入默认使用白名单，不默认允许所有人；
- Hermes Kanban REST/插件接口只绑定本机或受保护网络，不直接暴露公网；
- Lark CLI 与 Hermes 飞书工具由统一适配器封装，业务执行器不得直接散落调用；
- 真实验证使用测试群、测试文档和可控素材。
