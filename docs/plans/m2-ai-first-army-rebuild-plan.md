# A君军团：从固定问答到真正 AI 管家的重建计划

| 项目 | 内容 |
| --- | --- |
| 状态 | 已确认，准备执行 |
| 日期 | 2026-07-22 |
| 给谁看 | 负责人，不要求懂技术 |
| 最终目标 | 在飞书里拥有一支能独立干活、能被 A君 协调、出错有人接手的 AI 员工军团 |

## 先说结论

现在的 A君 还不够好用。它已经能处理少数几类事情，但很多时候仍靠识别固定说法；换一句自然说法，就可能答错、追问错或不接任务。

这不是负责人不会用，而是当前实现方向有问题。

这份计划确定：以后 A君 先用 AI 理解人话，再根据真实员工、真实进度和安全边界行动。固定规则只保留给安全和事实保护，不能再拿固定规则充当“理解能力”。

## 昨天为什么会走偏

昨天投入的工作并不只有一个固定问答，但主要精力花在了“某一句话答错，就补一条特殊处理”上。

结果是：

- 代码里积累了很多针对“进度”“继续”“需要”“你是谁”“多少员工”等说法的特殊判断；
- AI 虽然被接入，却排在这些特殊判断后面，很多消息根本不会交给 AI 理解；
- AI 当前更像“把一句话归到某个标签”的助手，还不是能理解目标、安排工作、跟进结果的管家；
- 自动测试很多，但不少测试使用预设的 AI 回答，证明的是“代码能按预设返回”，不是“真实飞书里自然聊天能用”。

因此，昨天的产出看起来增加了很多能力，实际用户体验却仍像一个演示版机器人。这是实施方向的错误，后续不再继续沿用。

## 最终使用方式

负责人在飞书里有两种入口：

1. 知道找谁时，直接找专业员工。
2. 不知道找谁、事情复杂时，直接找 A君。

例如：

- 直接把视频链接发给小D，小D自己完成整理并交付；
- 对 A君 说“研究几个竞品，最后给我行动方案”，A君自己理解目标、安排合适员工、盯住进度，最后汇总结果；
- 不需要记口令，不需要输入“继续”“选择 2”“查看状态”等固定命令。

第一批只让真正能独立交付的员工出现在飞书：

| 员工 | 负责人可以交代什么 |
| --- | --- |
| A君 | 不知道找谁、多人协作、查看全局、催办和汇总 |
| 小D | 视频、音频和公开素材整理 |
| 公开资料报告员 | 查找、阅读和对比公开网页资料 |

运维官、审核官、架构师、技术专家先在后台工作。只有它们有可独立交付的真实工作后，才增加飞书入口；不为了看起来热闹制造空壳员工。

## 三块东西各管什么

| 地方 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| 飞书 | 下任务、看关键进度、收结果、点击同意或拒绝 | 保存真实工作进度 |
| A军控制台 | 保存真实员工、任务、故障、产物和待测试项 | 变成第二个聊天软件 |
| Paperclip | 管新员工、权限、预算、多人长期工作和审计 | 卡住普通小任务 |

普通的视频整理、公开网页阅读等工作，直接由 A君 和对应员工完成。只有创建员工、扩大权限、花钱、外发、公开发布、删除内容或多人长期协作，才进入 Paperclip。

## A君和员工怎样工作

每次收到一句话，A君 先看：

- 负责人最终想得到什么；
- 当前聊天前面正在讨论什么；
- 哪些员工真的会上岗、真的有能力；
- 当前工作做到哪一步；
- 是否含有登录、花钱、发布、删除、外发或扩大权限等风险。

然后只做四种决定：

1. 只是提问：读取真实记录后回答。
2. 一名员工能完成：直接交给该员工。
3. 多人才能完成：拆成几项工作并汇总。
4. 当前没人能完成：说清缺什么，让架构师给出最小补齐方案；不得假装已经做完。

每名业务员工也应自己理解人话、完成工作、检查结果。A君 不替小D做视频整理，小D 也不等 A君 传固定口令。

固定规则只能用于：

- 不允许编造员工、进度和结果；
- 不允许绕过危险操作的确认；
- 不允许重复消息创建重复工作；
- 不允许没有产物和检查证据就说“已完成”。

## 什么才算完成

一件工作只有同时满足以下条件，才算完成：

1. 要求的报告、文档、文件或其他结果确实存在；
2. 执行员工已经按本岗位标准检查过；
3. 结果能打开、阅读或使用；
4. 结果已回到原来的飞书聊天；
5. 飞书回复、控制台状态和实际结果一致。

员工只回复“正在处理”或“已整理”，不算完成。

工作可能进入的真实状态：

```text
已接单 → 已安排员工 → 正在工作 → 检查结果 → 已交付
```

也可能出现：缺材料、等负责人同意、运维官处理中、技术专家处理中、待测试、确定失败。任何状态都必须如实说明，不能消失，也不能说成完成。

## 出错后的处理

```text
员工出错
→ 运维官先做一次安全处理
→ 仍无法恢复，交给技术专家
→ 暂时无法验证，标为“待测试”
→ 其他不相关工作继续推进
```

系统最多自动重试一次，避免无休止循环和浪费。电脑或服务重启后，工作必须从原进度继续；如果无法继续，必须保留记录并说明卡点。

## 测试方式

以后每项能力都按这个顺序验证：

1. 自动检查：先排除明显错误。
2. 本机真实工作：用真实网页、视频、文件或受控故障验证结果。
3. 运行中的程序核对：确认实际运行的就是新代码，而不是旧程序。
4. 飞书真人验收：前面通过后，负责人只做最后一次关键操作。

所有暂时无法人工测试的项目进入统一清单，写清测试方法、通过标准和卡点。一项卡住，只阻止它被宣布完成，不阻止其他独立工作继续。

## 实施顺序

### 第一轮：重做 A君理解方式

目标：任何正常中文先交给 AI 理解，再用真实员工和安全规则校验。

完成标准：准备一组不重复、没有固定模板的中文说法；A君 能正确回答、派人或自然追问，不需要负责人背指令。

### 第二轮：证明三名真实员工

目标：A君、小D、公开资料报告员都能独立完成一整件真实工作。

完成标准：负责人既能直接找员工，也能找 A君；两种入口看到的是同一项真实工作和同一个结果。

### 第三轮：证明任务和故障链

目标：工作从接单到交付、从故障到接手都可追踪。

完成标准：人为制造一次受控故障，确认运维官、技术专家和最终结论都有真实记录。

### 第四轮：收敛控制台和 Paperclip

目标：控制台只展示真相；Paperclip 只处理公司级风险。

完成标准：飞书、控制台和实际产物一致；普通小任务不被审批卡住，危险任务不会绕过确认。

## 分工

### 由实施者自行完成

- 设计、代码、自动检查、本机真实测试、运行状态核对；
- 故障修复、测试清单、验收记录和文档更新；
- 先让系统达到可用状态，再集中交给负责人做少量飞书验收。

### 只有负责人必须参与

- 飞书里的最后一次真人确认；
- 登录、验证码、付费、公开发布、删除、账号授权等必须由负责人决定的事情。

## 决策记录

| 决策 | 结论 | 原因 |
| --- | --- | --- |
| 飞书入口 | A君 + 真实专业员工双入口 | 既保留“直接找人”的效率，也保留“什么都交给管家”的方便 |
| 理解方式 | AI 优先 | 负责人不应学习固定命令 |
| 固定规则 | 只做安全与事实保护 | 防止固定规则继续代替理解能力 |
| 第一批员工 | 只保留三名真员工 | 先证明真实交付，不堆空壳 |
| 测试 | 自动、本机真实、运行核对、飞书真人四层 | 避免代码通过但真实不可用 |
| 卡住的测试 | 明确标为待测试，其他工作继续 | 不让外部条件拖住整体目标 |

## 本轮落实记录（2026-07-22）

已经做到：

- A君、运维官、任务协调官、架构师、审核官、创建官、技术专家都建立了各自独立 Hermes 身份；没有复制小D或音视频转录 Agent 的会话、工具或密钥。
- 六名后台员工都有独立岗位卡：负责什么、第一件小任务、不做什么、怎样才算完成，已放到各自 `agents/<员工>/岗位卡.md`。
- A君 的正常中文现在先交给 AI 判断；只有“暂停、继续、短确认、评价”这类必须依赖当前任务真相的话，才不让 AI 猜。AI 临时不可用时，旧的安全识别仍可保底。
- 自动检查已经覆盖“独立身份不被误当上线”“正常中文先走 AI”“检查系统有没有问题不被误判成负面评价”。

还不能写成完成：

- 新建的独立身份已经选好与音视频转录 Agent 相同的模型，但密钥仍只在原 Profile 内。用 A君和运维官的独立身份做了无副作用模型检查，均无法调用模型；所以只能算“身份、岗位和模型选择已建”，不能算“独立员工可聊天”。
- 当前运行中的 A君 暂时借用了小D的 Hermes 身份。这是历史遗留，不符合独立员工目标；A君自己的 `ajun` 身份已建好，但在它配置独立模型前不能切换，否则会让现有总管失去 AI 理解能力。
- 飞书后台已经核对到现有应用列表；新员工 Bot 的创建、发布和每个应用自己的允许人员身份，必须逐个完成真实收发验收，不能拿其他 Bot 的身份复用。

下一条最小闭环：先给 **A君独立身份** 配好模型，再切换 A君；之后给 **运维官** 建独立飞书 Bot，并只验证“检查军团有没有问题 → 真实报告回原聊天”这一件事。通过后再复制到其余后台员工。
