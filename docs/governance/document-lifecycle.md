# 文档迭代与治理规范

| 字段 | 内容 |

## 1. 目的

保证 Agent军团的产品目标、设计、代码和真实运行状态能够互相对应，同时避免所有小改动都被重流程拖慢。

## 2. 文档分层与唯一事实来源

| 问题 | 唯一事实来源 |
| --- | --- |
| 项目为什么做、长期走向哪里 | `tasks/prd-agent-army-master.md` |
| 当前里程碑做什么、如何验收 | 对应里程碑 PRD |
| 用户如何完成任务 | `docs/design/` 下的用户流程 |
| 界面状态、文案和操作 | `docs/design/` 与对应原型 |
| 系统组件和数据真相归属 | `docs/architecture/` |
| 跨系统字段和状态含义 | `docs/contracts/` |
| 目录、代码和测试规则 | `docs/standards/` |
| 为什么做出重要技术选择 | `docs/adr/` |
| 是否真的完成 | `docs/reviews/` 中的验收证据 |
| 工作如何安全交给下一位执行者 | `docs/handoffs/` 中的交接单 |
| 当前阶段和所有入口 | 根目录 `README.md` |

同一事实只能有一个正式定义。其他文档使用链接或摘要引用，不复制完整规则。发生冲突时，先修正唯一事实来源，再同步引用方。

## 3. 文档状态

正式文档使用以下状态：

```text
草案 → 待确认 → 已确认 → 实施中 → 已验收 → 已归档
```

- **草案**：可讨论，不允许作为实现承诺。
- **待确认**：内容完整，等待负责人确认。
- **已确认**：可以作为设计或实现依据。
- **实施中**：对应工作已经开始，范围变化必须留痕。
- **已验收**：验收标准和真实验证均完成。
- **已归档**：已被替代或不再有效，仅供追溯。

架构、契约和规范类文档可以使用“生效”代替“已确认”，但必须写版本与更新日期。

## 4. 四道硬门禁

### 4.1 里程碑启动门禁

开始里程碑前必须具备：

- 总 PRD 中的里程碑位置；
- 已确认的子 PRD；
- 清楚的范围、非目标和验收标准。

### 4.2 UI 编码门禁

涉及用户流程或界面的工作开始前必须具备：

- 已确认的主流程和异常流程；
- 对应界面状态、主操作和关键文案；
- 对高返工界面的原型评审。

纯后端、小修复和不改变工作流的局部调整不触发该门禁。

### 4.3 跨系统编码门禁

涉及飞书、Paperclip、Hermes 或其他外部平台前必须具备：

- 输入输出契约；
- 状态与数据真相归属；
- 权限和凭据边界；
- 已知失败状态与补偿方式；
- 对当前版本真实能力的最小验证结果。

### 4.4 完成门禁

任务标记“已验收”前必须具备：

- 相关自动化测试结果；
- 按风险要求完成的真实运行验证；
- 验收记录或证据位置；
- PRD、架构、契约、README 或变更记录中受影响内容已同步。

## 5. 允许直接做的改动

以下改动通常不需要新增 PRD、原型或 ADR：

- 明确的错别字、链接和说明修正；
- 不改变接口和用户流程的小型缺陷修复；
- 同一技术方向内的内部重构；
- 测试补充、日志改进和安全的依赖补丁；
- 已确认设计中的局部视觉微调。

直接改动仍需完成与风险相称的验证，并在现有任务或变更记录中留下一句说明。

## 6. 必须升级评审的变化

出现以下任一情况时，必须暂停扩展并更新上游文档：

- 改变核心用户、产品目标或里程碑范围；
- 改变系统边界、数据所有权或任务完成定义；
- 新增外发、公开发布、敏感访问或扩权能力；
- 引入新的核心平台、工作流引擎或持久化技术；
- 破坏既有兼容性或需要迁移历史任务/产物；
- 显著增加长期运维、模型或基础设施成本。

## 7. 更新责任

- A 君确认业务目标、范围、权限和高风险决策；
- 实施者更新其改动直接影响的架构、契约、规范和验收记录；
- 验收者核对代码、运行结果和文档是否一致；
- 后续审核官负责检查上线与权限文档；
- 后续运维官负责运行状态、授权和恢复文档。

“这是另一个 Agent 写的”不能作为文档不一致的理由。最终合入者负责收敛冲突。

## 8. 归档与版本

- 小改动直接提升文档补丁版本或更新日期；
- 改变字段、状态或兼容性的契约变更提升主版本；
- 旧文档保留原内容，在顶部注明“已被替代”、替代日期和新文件链接；
- 归档文件放入 `docs/archive/`，不得继续作为实施依据；
- 删除历史文件前必须确认内容已被正式基线吸收且无追溯需要。

## 9. 每个里程碑的闭环

```text
总 PRD 定位
→ 子 PRD 确认
→ 用户流程与 UI 确认
→ 架构与契约确认
→ 实施计划
→ 编码和测试
→ 真实运行验收
→ 更新 README 与文档状态
→ 归档被替代内容
```

## 10. 交接文档闭环

跨人、跨 Agent、跨会话或涉及未完成运行/外部验证的工作，按 [项目交接与闭环](../handoffs/README.md) 执行。交接单不是新的需求事实来源：它只引用总 PRD、里程碑 PRD、架构、契约和验收记录，并把当前证据、风险、唯一下一步和关闭条件压缩成可执行状态。

交接单进入“已关闭”前，必须完成：

- 接手或验收者补全验证账本；
- 最终证据写入对应 `docs/reviews/` 验收记录；
- 受影响的 PRD、README、架构或契约完成同步；
- 写明关闭时间和证据链接。

只有在满足以上条件后才可归档；被替代的交接单移入 `docs/archive/handoffs/`，并链接后继交接单或验收记录。
