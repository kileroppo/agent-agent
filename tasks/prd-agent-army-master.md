## 1. 项目概述

Agent军团是一套以飞书为主要工作入口、由多个专业 Agent 接受任务、执行工作、交付结果并接受组织治理的数字员工系统。

项目首先解决“真实工作能否稳定交给 Agent 完成”的问题，而不是先建设 Agent 创建平台、Agent 商城或面向外部客户的 SaaS。第一阶段以小D音视频转录整理 Agent 为样板，跑通从任务发起到结果交付、失败恢复和治理审计的完整闭环，再按真实业务需求扩展其他岗位。

## 2. 要解决的问题

当前已有小D本地网页原型和音视频处理能力，但它仍是一个独立工具，尚未形成军团级系统：

- 用户不能在飞书内完成任务提交、状态查看和结果接收；
- Agent 缺少统一的岗位、能力、权限和质量标准；
- 任务缺少组织级归属、预算、审批和审计；
- 执行状态、产物和失败恢复尚未形成统一契约；
- 项目缺少能够持续维护的 PRD、架构、UI、代码与验收文档闭环。

## 3. 目标

- 让用户能够在飞书内调用真实 Agent 完成工作并接收可用产物；
- 让每个 Agent 都有明确岗位、允许工具、权限边界和质量标准；
- 让任务从发起、执行、审批、交付到复盘均可追踪；
- 建立可扩展但不过度设计的军团级技术架构；
- 建立“需求—设计—实现—验证—归档”的文档迭代闭环；
- 通过真实业务频率和可验收价值决定是否扩编 Agent。

### 3.1 当前产品化目标

以本项目资料中“亦仁 Agent 军团”的日常体验为对标：用户主要向“ A君·军团总管”交代目标；总管理解、分工、跟进、处理普通故障并主动汇报，用户只在高风险动作和质量判断时介入。当前常驻员工为 A君、小D、小R、办公执行助理和运维官；创建官、审核官、架构师和技术专家作为 Paperclip/Hermes 后台按需能力保留。任务协调官职责并入 A君，小G的 GitHub 公开检索并入小R。每名正式员工都必须拥有独立身份、职责、Profile、权限边界和可验收任务；只有 `interaction.directFeishu=required` 的岗位保持独立飞书 Gateway。

单项外部测试、人工点击或平台条件暂时卡住时，该项进入统一验收账本的“待测试/等待外部条件”，不能因此暂停其他独立能力开发；未验证项也不能写成已完成。

## 4. 目标用户

### 4.1 当前用户

- 主要用户：A 君；
- 次要用户：闭环稳定后加入的少量内部团队成员；
- 治理角色：后续的 Agent 架构师、审核官、运维官和技术专家。

### 4.2 暂不服务

- 外部企业客户；
- 公共 SaaS 注册用户；
- Agent 模板交易、FDE 服务或 Agent 商城用户。

## 5. 产品原则

1. **真实交付优先**：Agent 的价值由最终产物是否可用证明，而不是由消息是否发送或模型是否返回证明。
2. **飞书工作流优先**：用户在飞书完成主要操作，管理与调试入口不抢占主流程。
3. **低风险自动化，高风险审批**：普通任务自动执行；外发、公开发布、敏感访问、扩权和高成本动作需要审批。
4. **可靠性优先于速度**：任务不能静默丢失，部分成功不能冒充完整成功。
5. **按真实需求扩编**：只有稳定、重复、可验收的职责才创建新 Agent。
6. **少量硬门禁**：只对高返工或高风险节点强制评审，小改动保持灵活。
7. **先闭环，再规模化**：先让任务边界、权限、质量、成本与失败恢复可控；再扩大并发 Agent、任务量或模型调用。Token 消耗不作为成功指标。

## 6. 总体用户流程

```text
用户在飞书“ A君·军团总管”提出任务
→ Hermes 将命令送到 Mac，系统识别岗位和任务类型
→ 创建带唯一 ID 的标准任务
→ Hermes 创建执行任务并驱动对应 Agent
→ 飞书展示必要状态或请求补充信息
→ 本次范围明确的审批在飞书卡片+A君闭环；组织级动作按需进入 Paperclip 审批
→ Agent 生成并验证产物
→ 飞书交付文档、附件和结果摘要
→ 记录成本、错误、反馈和改进机会
→ 需要组织级治理时，由 Paperclip 统一管理目标、组织、组织级任务、heartbeat、预算、审批与审计
→ 执行 Agent 通过受控适配器领取并回报工作；业务产物仍由各业务 Agent 验证
```

### 6.1 Paperclip 介入规则

不是每条飞书消息都创建 Paperclip 任务。低风险、单 Agent、输入完整且可立即完成的请求可由飞书 → Hermes → 业务 Agent 直接闭环，仍保留业务任务 ID、幂等键、checkpoint 和产物证据。

本次范围明确、不改变长期组织能力的一次性审批由飞书卡片和 A君审批记录闭环，不创建 Paperclip 任务。满足任一条件时，入站适配层才创建或关联 Paperclip 组织级任务：新 Agent、账号/权限扩展、公开发布、付费/预算；跨 Agent 协作或转交；长任务需要排队、定时或 heartbeat 唤醒；暂停/终止；或需要跨岗位统一追踪与审计。投影只包含任务 ID、飞书事件引用、标题/类型、负责人、状态摘要、预算/审批引用、产物引用和脱敏失败分类；不得复制原始聊天正文、媒体、字幕、Cookie 或业务 checkpoint。

## 8. 用户故事

### US-M-001：在飞书调用对应 Agent

**描述：** 作为主要用户，我希望直接在飞书提出任务并由合适的 Agent 接手，以便不切换多个工具。

**验收标准：**

- [ ] 用户能够从飞书发起至少一种真实业务任务；
- [ ] 系统返回任务 ID、承接 Agent 和接收结果；
- [ ] 无法识别或缺少输入时明确请求补充信息；
- [ ] 飞书交互通过真实客户端或浏览器环境验证。

### US-M-002：查看可信任务状态

**描述：** 作为主要用户，我希望知道长任务正在做什么，以便判断是否需要等待或介入。

**验收标准：**

- [ ] 状态来自真实执行阶段，不使用虚假百分比；
- [ ] 超时、失败、暂停和等待用户输入可以区分；
- [ ] 状态同步失败会留下可诊断记录；
- [ ] 部分成功不会显示为完整成功。

### US-M-003：接收并验证业务产物

**描述：** 作为主要用户，我希望在飞书收到可以访问的文档和附件，以便直接使用结果。

**验收标准：**

- [ ] 产物包含类型、来源、生成时间和访问位置；
- [ ] 系统交付前验证关键产物存在且可读取；
- [ ] 访问权限与预期接收人一致；
- [ ] 失败产物不会作为成功结果交付。

### US-M-004：治理高风险操作

**描述：** 作为最终负责人，我希望高风险操作在执行前请求审批，以便控制数据、权限和成本风险。

**验收标准：**

- [ ] 外部发送、公开发布、敏感访问、扩权和高成本动作可配置为需审批；
- [ ] 审批记录包含原因、范围、申请人、批准人和有效期；
- [ ] 普通低风险任务不会被不必要的审批阻塞；
- [ ] 拒绝或过期后默认不执行目标动作。
- [ ] 用户在飞书原会话的审批卡完成决定；不要求进入 A君网页。

### US-M-005：按标准扩展新 Agent

**描述：** 作为项目维护者，我希望新 Agent 遵循统一契约和验收标准，以便扩编时不复制一套不可治理的孤岛代码。

**验收标准：**

- [ ] 新 Agent 有版本化的 AgentManifest；
- [ ] 新 Agent 明确输入、产物、工具白名单和权限；
- [ ] 新 Agent 通过契约测试和真实任务验收；
- [ ] 新 Agent 在总 PRD 对应里程碑中有明确位置。

### US-M-006：在飞书提出并上线一个新 Agent

**描述：** 作为负责人，我希望在飞书描述一个新岗位需求，由系统生成可审核草案、完成受限测试并在通过后上线，避免手工拼装不可追溯的 Agent。

**验收标准：**

- [ ] 飞书创建入口只生成 `draft` AgentProposal，不直接创建生产 Agent；
- [ ] 草案包含岗位边界、Prompt/Skills 候选、运行时、最小权限、预算和验收任务；
- [ ] Paperclip 审核批准后才允许创建隔离测试实例；
- [ ] 测试实例以受限工具、预算和数据完成一条验收任务；
- [ ] 通过后才可标记 `active` 并被飞书路由；失败保持可修订，不伪造上线；
- [ ] 新 Agent 不得因创建流程获得未批准的账号、外发、发布、付费或扩权能力。

## 9. 功能需求

- **FR-1：** 系统必须支持从飞书接收任务并返回唯一任务 ID。
- **FR-2：** 系统必须根据明确规则将任务分配给对应 Agent；无法分配时不得静默猜测。
- **FR-3：** 系统必须记录任务归属、状态、优先级、成本或预算信息。
- **FR-4：** 系统必须支持长任务阶段状态、失败记录、重试边界和断点恢复。
- **FR-5：** 系统必须在交付前验证关键产物存在、可读取且权限正确。
- **FR-6：** 系统必须区分普通自动执行动作和需要人工审批的高风险动作。
- **FR-7：** 系统必须记录关键操作、审批、失败和最终结果，满足问题追溯需要。
- **FR-8：** 每个 Agent 必须使用统一的岗位、任务、产物和审批契约。
- **FR-9：** 系统必须能够采集每个任务的模型/工具消耗和结果反馈，为后续优化提供依据。
- **FR-10：** 项目必须通过根 README 展示当前里程碑、正式文档入口和真实完成状态。
- **FR-11：** 需要网站或软件登录态的 Agent 必须经由受控账号管家调用；凭据不得进入 Agent、聊天、任务、日志或产物。
- **FR-12：** 账号连接必须绑定平台、允许动作、Agent、数据范围、有效期、审批与可撤销状态；连接健康不是业务任务成功的证据。
- **FR-13：** 所有 Agent 必须经由统一内容获取中心读取外部内容；中心优先使用支持该平台的深度适配器，不能使用时按能力范围切换到通用适配器，业务 Agent 不直接绑定具体工具。
- **FR-14：** 运维官必须基于脱敏连接、适配器和任务健康事件执行诊断、通知与低风险恢复；不得读取凭据、绕过平台控制或擅自扩大授权。
- **FR-15：** Paperclip 必须作为军团的唯一组织级任务与调度总控，承载目标层级、岗位/汇报关系、心跳唤醒、预算、审批和审计；不得由 A君复制同类控制台或第二套任务队列。
- **FR-16：** A君是受控本机能力底座：负责连接授权、内容获取、组件托管、执行适配、业务产物诊断与恢复提示；它向 Paperclip 同步标准任务引用和执行回报，不替代 Paperclip 的组织和调度职责。飞书是日常派活与交付入口；A君局域网页只作为授权、诊断和应急入口。
- **FR-17：** 系统必须按 Paperclip 介入规则路由任务：简单单 Agent 任务不得因治理投影增加不必要中转；符合组织级治理条件的任务必须以飞书事件幂等键创建或关联 Paperclip 任务，并只同步最小脱敏任务信封。
- **FR-18：** 系统必须支持飞书创建 Agent 草案；草案经 Paperclip 审核、受限测试实例和验收任务通过后，才可从 `draft` 进入 `active`。
- **FR-19：** 系统必须以飞书“ A君·军团总管”作为主要日常手机入口，同时允许老板按需私聊任何已上岗的业务或治理员工。每名独立员工必须使用自己的 Hermes Profile、会话/记忆、岗位 Prompt、Skill/MCP 作用域和飞书应用；群内仅响应 @ 提及。只有通过本机岗位任务和真实飞书回归的员工才标记为直聊可用；入口、任务、审批和产物仍只引用 A君/Paperclip 的同一份真相。
- **FR-20：** 系统必须按审批分流执行：一次性、范围明确且不改变组织能力的决定由飞书卡片和 A君审批记录闭环；新 Agent、扩权/连接、公开发布、付费/预算、跨 Agent 长任务、暂停/终止或组织级审计必须进入 Paperclip。两条路径都必须在继续执行前校验批准人、范围、有效期和幂等性。
- **FR-21：** 架构师必须区分当前事实、架构判断和未来候选方案。当前事实引用活动 Manifest、真实任务类型和近期任务记录；架构判断说明依据、假设和置信度；候选方案允许提出当前不存在的新岗位、能力或接口，但必须附最小验证计划、风险和非目标，验证前不得冒充已实现。
- **FR-22：** 技术专家必须先按代码、授权/权限、输入/来源、外部瞬时和未知进行故障分流；只有真实存在的代码与测试路径可以进入受控修复，其余故障交付诊断、恢复入口或补充材料要求，不得盲改代码或把诊断冒充修复。
- **FR-23：** 仓库必须提供只读、机器可读的运行指纹，至少区分当前源码 Git 身份与脏状态、关键监听 PID/cwd、A君不可变 release/payload/Git 身份以及 A君、Paperclip、小D和 Publisher 的白名单健康字段；不得读取或输出 Secret，不得修改服务、Campaign、Cron、审批或外部平台状态。
- **FR-24：** 新业务任务必须以 Business Workflow 为主对象，跨岗位步骤共享稳定 workflowId；任务成功、可读产物、关键质量门和人工验收必须分层判断，任何聊天回复、Manifest active 或进程在线都不能单独证明业务完成。
- **FR-25：** Model 只能提出能力请求。已登记、同机或公开只读、费用已知且预算内的能力可由 Policy 自动批准；私有/登录态/跨设备需本次本机授权，外部写入、扩权和超预算继续由 Paperclip 批准。可恢复本机能力最多自动恢复一次、重试一次。
- **FR-26：** 新增 Workflow、Policy、Evaluation 和核心 Interface 默认使用 TypeScript；旧 JavaScript Provider 通过 Adapter 渐进接入，禁止为迁移而复制业务逻辑或形成第二套控制面。

## 10. 非功能需求

### 10.1 性能与规模

- 初期服务 1 位主要用户和少量内部成员；
- 同时运行 3–10 个任务；
- 长音视频允许分钟级到小时级处理，但必须提供真实状态；
- 第一阶段不追求公网高并发。

### 10.2 安全与隐私

- 默认本地或单组织部署，治理后台不直接暴露公网；
- Agent 使用最小权限和工具白名单；
- secret、token、Cookie 和授权链接不得进入提示词、聊天、日志或文档；
- 敏感数据访问和外部发送必须可审批、可撤销和可追踪。

### 10.3 可靠性

- 每个任务具有唯一 ID、明确状态和幂等键；
- 外部接口失败必须保留真实原因；
- 长任务使用持久化阶段状态与 checkpoint；
- heartbeat 只代表存活，产物验证才代表业务完成；
- 第一阶段不承诺 7×24 小时企业级可用性，但关键状态和产物必须可备份、可恢复。

### 10.4 维护性

- 飞书、Hermes 以及 M2 起的 Paperclip 必须通过适配层接入；
- 业务逻辑不得直接绑定某个平台 SDK；
- 只有出现真实复用场景后才提取公共模块；
- 重要架构变化使用 ADR 记录原因和替代方案。

## 11. 设计与技术约束

- 飞书是日常任务、状态和交付入口；A君本地界面只承载授权、诊断、恢复和必要的应急手工入口；
- Paperclip 从 M2 起负责公司目标、组织树、岗位/汇报关系、组织级任务、心跳调度、预算、组织级结构化审批和跨 Agent 审计，是军团唯一总控；普通一次性审批由 A君保存最小记录；
- Hermes、Codex、Claude Code、Cursor、OpenClaw、脚本或 HTTP 服务都可作为 Paperclip 管理的执行运行时，具体接入以适配器和真实验收为准；
- A君是可扩展的本机能力底座和执行适配层：通过稳定的能力、连接、内容与恢复契约隔离 ASR、下载器、浏览器伴侣和平台适配器；不建设军团组织、任务调度、预算或审批的重复控制台；
- Codex 或其他工程模型用于建设、适配和复杂技术任务；
- M1 不开发军团管理后台，也不接入 Paperclip；
- 现有小D网页保留为本地调试和应急入口；
- OpenClaw、LangGraph 等候选技术必须通过同一真实任务验证后才能进入既定架构。

## 12. 非目标

- 不建设公共 SaaS、多租户计费或开放注册；
- 不建设 Agent 商城或低代码 Agent 生成平台；
- 不为了匹配参考截图一次性创建 30 个空壳 Agent；
- 不自研与 Paperclip 重复的军团管理后台、任务队列、心跳调度、预算或审批中心；
- 不承诺无人值守自动执行所有高风险动作；
- 不以 Token 消耗量作为业务成功指标；
- 不把尚未验证的外部项目能力写成已实现事实。

## 13. 成功指标

- M1 至少完成 3 次真实飞书端到端任务，其中包含 1 次长任务；
- 关键任务丢失率为 0；
- 成功任务的关键产物可访问验证通过率为 100%；
- 至少验证 1 个可恢复失败场景；
- 高风险动作未经批准执行次数为 0；
- 每个已上线 Agent 均有 Manifest、契约测试和真实验收记录；
- 每个已完成里程碑均同步更新 PRD 状态、验收证据和根 README。

## 14. 文档与迭代闭环

每个里程碑遵循：

```text
总 PRD 定位
→ 子 PRD 定义范围与验收
→ 用户流程与 UI 确认
→ 架构和契约确认
→ 实施计划
→ 编码与测试
→ 真实运行验收
→ 更新状态与变更记录
→ 归档被替代文档
```

小而明确的改动可以直接实施；涉及系统边界、权限、数据所有权、核心工作流或长期维护成本的变更必须先更新对应设计或 ADR。

## 15. 依赖与风险

| 风险 | 应对方式 |
| --- | --- |
| Hermes 或飞书能力与设想不同 | M1 实装前做隔离验证，适配器隔离差异 |
| M2 Paperclip 能力与设想不同 | 先以一个低风险执行 Agent 验证任务、heartbeat、预算、审批和回报链路；未验证前不让 A君复制或替代其总控职责 |
| 多系统状态漂移 | 统一任务 ID、状态映射、幂等键和同步失败记录 |
| 飞书原型无法实现 | UI 只使用飞书真实支持的组件和交互 |
| 军团范围失控 | 以里程碑和真实业务验收作为扩编门槛 |
| 文档落后于代码 | 未更新相关文档不得标记为已验收 |
| 本地单点故障 | 持久化关键状态和产物，建立备份恢复流程 |
| 权限或数据泄露 | 最小权限、凭据隔离、高风险审批和审计 |
